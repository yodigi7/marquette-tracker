# Spec Delta

## MODIFIED Requirements

### Requirement: Fill mode controls when the post-Peak tail begins

The system SHALL provide two persisted fill modes. The configured post-Peak tail boundary is `peakDay + postPeakDays + 1`, where `peakDay` is the latest user-entered monitor Peak day. Mucus Peak values MUST NOT anchor or extend the tail. With the default `postPeakDays = 4`, a monitor Peak on day P is followed by post-Peak days P+1 through P+4 and the first automatic Low candidate is P+5. In `auto-after-window` mode, once a monitor Peak is known, the first eligible generated date is that configured boundary. In `after-user-low` mode, the system SHALL wait for the first user-entered `monitor: low` on or after that boundary, SHALL generate only on dates after that Low, and SHALL leave earlier gaps in the configured post-Peak tail without data. A user-entered monitor High at or after the active tail start SHALL stop the current tail; a later user-entered monitor Peak SHALL begin a fresh tail under the active mode.

#### Scenario: Automatic mode starts at the configured post-Peak boundary

- **GIVEN** a cycle has a known monitor Peak and the fill mode is `auto-after-window`
- **WHEN** the post-Peak tail is reconciled
- **THEN** generation begins on the configured boundary `peakDay + postPeakDays + 1`
- **AND** no date before that configured boundary is retroactively filled

#### Scenario: Configured tail boundary remains authoritative after historical-window rules

- **GIVEN** a cycle has latest monitor Peak day `P`, configured `postPeakDays` value `N`, and historical rules produce an earlier calendar window end
- **WHEN** `auto-after-window` evaluates the post-Peak tail
- **THEN** the first eligible generated date is cycle day `P + N + 1`
- **AND** derived status coloring still uses the applicable historical window end
- **WHEN** `after-user-low` evaluates the same tail
- **THEN** a user Low before cycle day `P + N + 1` cannot become the anchor
- **AND** after a qualifying user Low, generated records begin on the following date

#### Scenario: User-anchor mode waits for a qualifying Low

- **GIVEN** the fill mode is `after-user-low` and a cycle has gaps in the configured post-Peak tail
- **WHEN** the user enters the first qualifying post-Peak Low
- **THEN** earlier gaps remain without data
- **AND** generated records may begin only on the following date

#### Scenario: A Low before the configured tail boundary does not qualify

- **WHEN** a user-entered Low occurs before the configured post-Peak tail boundary
- **THEN** it does not become the anchor for `after-user-low` generation

#### Scenario: Default automatic mode uses the monitor-only four-day boundary

- **GIVEN** the default `postPeakDays` value and a user-entered monitor Peak on cycle day 14
- **WHEN** `auto-after-window` reconciles the cycle
- **THEN** generation begins on cycle day 19
- **AND** no date before day 19 is retroactively filled

#### Scenario: Mucus does not activate automatic fill

- **GIVEN** a cycle has a mucus Peak but no user-entered monitor Peak
- **WHEN** post-Peak fill is reconciled
- **THEN** no inferred Low tail is generated from that mucus Peak

#### Scenario: A monitor High stops the active tail

- **GIVEN** an active inferred Low tail has reached at least its configured start date
- **WHEN** the user enters a monitor High on or after that start date
- **THEN** no new inferred Low dates are generated after the High
- **AND** inferred rows after the High that are no longer eligible are removed or re-derived

#### Scenario: A later monitor Peak starts a fresh tail

- **GIVEN** a monitor High stopped the current inferred Low tail
- **WHEN** the user later enters another monitor Peak
- **THEN** the new monitor Peak becomes the basis for a fresh post-Peak fill window
- **AND** the new window receives its own 30-generated-row budget

### Requirement: Generated tails respect date, cycle, and count boundaries

The system SHALL never create a generated record for a future date. For the open/current cycle, generation SHALL stop at today. For an older cycle, generation SHALL stop at the day before the next Menses/new-cycle boundary when that boundary is known. Each configured post-Peak tail SHALL contain no more than 30 autogenerated Low records in the current inference window. A user-entered monitor High stops the current tail; a user-entered monitor Peak or a cycle/window change starts a new limit. A user-entered Low or other non-structural user data SHALL not reset the limit while the same tail remains active.

#### Scenario: Open cycle stops at today

- **GIVEN** an open cycle has a monitor Peak and an eligible post-Peak tail
- **WHEN** the current date is before the next Menses day
- **THEN** generated records may be created through today only
- **AND** no future record is created

#### Scenario: Closed cycle stops before the next Menses day

- **GIVEN** an older cycle has a known following Menses day
- **WHEN** its post-Peak tail is generated
- **THEN** generation ends on the day immediately before that Menses day

#### Scenario: Thirty-record cap is enforced

- **GIVEN** an eligible post-Peak window already contains 30 autogenerated Low records
- **WHEN** another missing date would otherwise be generated
- **THEN** the system leaves that date without a generated record until the current tail is stopped or its window changes

#### Scenario: A High ends the run

- **GIVEN** an eligible tail has generated fewer than 30 Low records
- **WHEN** the user enters a monitor High after the tail start
- **THEN** later dates in that tail are not filled
- **AND** the High remains user-authored data

### Requirement: Generated readings remain non-menses observations

An autogenerated Low record SHALL participate in stored data, record coverage, day-result display, and final cycle membership/day assignment as a non-menses day when interpretation is enabled, but it SHALL NOT be used as monitor evidence, Peak evidence, fertile-window begin/end evidence, or cycle-placement boundary evidence. The calendar's fertile/infertile coloring SHALL remain derived from the applicable monitor-only window and the day's context, not from the raw Low value alone. When interpretation is disabled, the existing algorithm-off hiding and retention rules apply.

#### Scenario: Generated Low does not create a Peak

- **WHEN** a post-Peak tail contains generated Low records
- **THEN** the engine still derives its Peak and fertile-window end from actual user-entered monitor Peak evidence
- **AND** generated Low records are not counted as Peak evidence

#### Scenario: Generated Low participates in coverage when interpretation is enabled

- **GIVEN** interpretation is enabled and inferred Low records exist after the configured post-Peak interval
- **WHEN** the Calendar, chart, and record-coverage views render the cycle
- **THEN** those assumed days can be displayed
- **AND** the assumed days do not change the monitor-only Peak or fertile-window result

#### Scenario: Low before the configured tail boundary remains contextual

- **WHEN** a Low occurs before the configured post-Peak tail boundary
- **THEN** its display state is determined by the applicable monitor-only fertile-window rules
- **AND** it is not automatically labeled infertile solely because the monitor value is Low

### Requirement: Reconciliation preserves user data and invalidates stale generated tails

Whenever a user saves, edits, deletes, or changes settings that can affect cycle placement, the monitor Peak/window, or the fill mode, the system SHALL re-derive the affected structure and reconcile autogenerated records. A user-entered Menses or monitor High SHALL invalidate downstream autogenerated records that are no longer eligible; a user-entered monitor Peak SHALL establish a fresh post-Peak window. Reconciliation SHALL never delete or overwrite user-authored fields, and unrelated user data such as notes or BBT SHALL not by itself invalidate an eligible tail.

#### Scenario: Backfilled Menses invalidates the old tail

- **GIVEN** generated Low records exist after a configured post-Peak tail
- **WHEN** the user backfills a Menses record before those generated dates
- **THEN** the system re-derives the new cycle boundary
- **AND** removes or re-derives generated records that belonged to the invalidated tail
- **AND** preserves the user's Menses record

#### Scenario: A new Peak reopens the configured post-Peak tail

- **WHEN** a user-entered monitor High or Peak changes the latest applicable monitor Peak or post-Peak boundary
- **THEN** generated records that fall before the new eligible tail are invalidated
- **AND** the new tail is reconciled under the active mode and cap

#### Scenario: A monitor High stops the old tail

- **WHEN** a user-entered monitor High occurs after the active tail start
- **THEN** generated records after that High are invalidated
- **AND** the user High is preserved

#### Scenario: A new monitor Peak reopens a fresh tail

- **WHEN** a user-entered monitor Peak occurs after a stopped tail
- **THEN** generated records before the new eligible tail are invalidated
- **AND** the new tail is reconciled under the active mode, four-day default, and cap

#### Scenario: Notes do not invalidate a tail

- **WHEN** the user adds notes or BBT to a date in an eligible generated tail without changing cycle or monitor Peak evidence
- **THEN** the existing generated tail remains eligible
- **AND** the user's additional fields are preserved
