# Proposal

## Why

Sparse daily logging leaves large unexplained gaps in a cycle, while the existing placement and calendar behavior only understands explicitly stored records. The app needs a controlled way to reconstruct the post-Peak infertile tail: either automatically from the configured post-Peak boundary or after the user enters the first qualifying Low, without presenting assumed readings as user observations.

## What Changes

- Add an autogenerated-data provenance model for stored Day Records so inferred `monitor: low` readings are real persisted records but remain distinguishable from user-entered observations.
- Add a post-Peak tail reconciliation policy with two persisted modes:
  - automatically fill from the configured post-Peak tail boundary `peakDay + postPeakDays + 1`, where `peakDay` is the latest monitor/mucus Peak; or
  - wait for the first user-entered `monitor: low` on or after that configured boundary, then fill only after that date without retroactive gap filling. The historical calendar end, when it is earlier, still controls derived display status but does not change this fill boundary.
- Persist inferred Low records only through today, never into future dates, and never beyond the next Menses/new-cycle boundary.
- Limit each post-Peak window to 30 consecutive autogenerated Low records; the allowance resets only when the cycle or post-Peak window changes.
- Re-derive and reconcile generated records when a user backfills or changes a Menses, High, Peak, or other record that changes the relevant cycle/window context; generated rows are real non-menses records assigned to the final derived cycle, but are not used as boundary evidence during the initial placement pass; never remove user-authored data during reconciliation.
- Treat explicit deletion of an inferred record as a persistent suppression for that date and inference basis, so reconciliation does not immediately recreate it; entering user data on the date clears the suppression, and a changed cycle/window no longer inherits an obsolete suppression.
- Make the fill mode immediately adjustable and persisted in Settings, with algorithm-off behavior that pauses new inferred generation while preserving provenance and allowing reconciliation when interpretation is re-enabled.
- Display inferred records distinctly in the Calendar/daily-entry experience while allowing the user to edit or delete them.
- Keep the existing Marquette fertile-window rules intact: `Low` is a monitor reading, while infertile/Fertile coloring remains a derived contextual state. The configured post-Peak fill boundary is a separate generation policy and does not rewrite the engine's historical window calculation.

## Capabilities

### New Capabilities

- `post-peak-fill`: Persisted, provenance-aware reconstruction and reconciliation of inferred post-Peak Low readings.

### Modified Capabilities

- `calendar`: Show and label autogenerated records, support user overrides, and keep inferred tail changes consistent with globally re-derived cycle placement.
- `app-settings`: Add and persist the post-Peak fill mode and expose its interaction with the algorithm toggle and post-Peak-day setting.

## Impact

- Pure engine and reconciliation logic for identifying post-Peak windows and eligible missing dates.
- Day Record types/repository metadata for origin, inference rule, and reconciliation lineage.
- Zustand/Dexie write and hydration paths, including global cycle replanning and invalidation of stale autogenerated rows.
- Calendar grid, day cells, and daily-entry form for provenance display and overrides.
- Settings UI and persistence tests.
- Engine, store, calendar, and settings tests; no new runtime dependency and no backend or export changes.
