# Design

## Context

The current store has a single placement-aware write path that re-partitions all records from logged blood-flow evidence. The pure engine derives the fertile window from actual monitor/mucus evidence, but the Calendar currently shades only dates that have a `DayRecord`; the cycle chart preserves missing-day gaps. The new feature adds persisted assumed Low records, so inference now has a durable data-model and reconciliation concern rather than being a read-only visual projection.

The existing settings row is a single persisted object with no indexed migration requirement for adding optional fields. The engine remains framework-agnostic and must continue to accept no React, Dexie, or browser APIs.

See `proposal.md` for motivation and `specs/` for the behavioral contract.

## Goals / Non-Goals

**Goals:**

- Represent inferred post-Peak Low readings as real Day Records with explicit provenance.
- Keep the tail policy pure, testable, and portable with the rest of the Marquette engine.
- Reconcile generated rows after user writes, settings changes, and global cycle replanning.
- Preserve user-authored data and make inferred records visibly distinct and editable.
- Keep future dates, cycle boundaries, the 30-record cap, and `postPeakDays` changes deterministic.

**Non-Goals:**

- No new Marquette begin/end rules; the existing Peak and historical window calculation remain authoritative for derived status. The configured post-Peak tail boundary is a separate generation policy for inferred rows.
- No interpolation of missing High/Peak readings and no retroactive filling in `after-user-low` mode.
- No cloud sync, export, notifications, or new dependency.
- No future-date generation or new standalone cycle-entity representation for inferred records.

## Decisions

### 1. Add record-level provenance, treating legacy rows as user data

Extend `DayRecordEntity` with an optional origin discriminator (for example, `dataOrigin: 'user' | 'inferred'`) and optional inference metadata containing the rule, Peak/anchor basis, and mode/version needed to re-evaluate the row. Rows without the field read as `user` for backward compatibility. A generated row contains only assumed data; a user edit through the existing entry form makes the resulting record user-authoritative while retaining lineage metadata where useful.

Persist explicit deletion as a small list of `PostPeakSuppression` values in the settings row. Each suppression stores the date, cycle id/Day 1, Peak day, post-Peak setting, and fill mode. The planner only applies a suppression whose basis still matches the current cycle/window. A user write on the date removes matching suppressions; a changed cycle or window naturally leaves old suppressions inactive.

Alternative considered: add provenance only in a parallel UI map. Rejected because records must remain correct after reload, sync, and edits, and a parallel map would lose the distinction during global replanning.

### 2. Keep fill planning pure and separate from persistence

Add a pure post-Peak fill planner under `src/core/engine`. It accepts cycle inputs, records, latest-Peak context, the persisted settings and suppressions, and an explicit `today` DateKey. It returns desired generated dates and stale generated record identities; it performs no I/O and imports no browser or database modules.

The planner treats `monitor: low` as a raw reading only. It derives the configured post-Peak tail boundary from the latest monitor/mucus Peak (`peakDay + postPeakDays + 1`), independently of any earlier historical `FertileWindow.end`; that historical end remains authoritative for derived display status. It never uses a user Low before that configured boundary as an anchor. In `after-user-low` mode, the anchor is a user-origin `monitor: low` on or after the configured boundary; generated rows cannot activate that mode.

Alternative considered: make the Calendar calculate generated cells on demand. Rejected because persisted rows must be reconciled after backfills and setting changes, and render-time inference would drift from the stored representation.

### 3. Derive structure from authoritative user evidence, then reconcile generated rows

Reconciliation follows this order:

```text
user records + pinned starts
        -> cycle placement and user-anchored boundaries
        -> engine windows / latest Peak
        -> desired post-Peak fill
        -> create or remove autogenerated rows
        -> assign all records and refresh output
```

Generated rows are real non-menses records and are assigned to the final derived cycle, but they are intentionally excluded from initial boundary discovery. Stale generated rows are not allowed to invent a boundary while the system is deciding which rows should exist. This avoids a feedback loop when a backfilled Menses record or newer Peak changes the placement.

The store runs the reconciliation in the same transaction as user/settings writes where practical. It performs one final cycle-row assignment after generated rows are created or removed. Because generated rows are excluded from initial boundary discovery and only extend an already identified post-Peak interval, a repeat planner pass is not required for the current policy; a bounded loop would be added only if future inference rules allow generated rows to affect boundaries. User rows are never candidates for automatic deletion.

Alternative considered: include every generated row in the first placement pass. Rejected because stale assumptions could split or merge cycles before the system knows which assumptions are still valid.

### 4. Reconcile by origin and preserve overrides

The reconciler compares desired generated dates with existing `dataOrigin: 'inferred'` rows and active post-Peak suppressions. It creates missing rows, removes stale generated rows, skips actively suppressed dates, and leaves user rows untouched. A user Menses, High, or Peak that changes the relevant cycle/window invalidates downstream generated rows. A user Low confirms/updates the relevant tail without resetting the 30-record allowance; notes, BBT, intercourse, and other non-structural fields do not invalidate an eligible tail. A user write on a suppressed date removes that date's suppression.

A generated row edited by the user becomes user-authoritative, so subsequent reconciliation cannot delete it without an explicit user action. This is preferable to preserving every edited row as generated, which would make an intentional correction look disposable.

### 5. Add two settings and make them trigger reconciliation

Add `postPeakFillMode: 'auto-after-window' | 'after-user-low'` to the settings row, defaulting to `auto-after-window`. The selector lives with the algorithm and `postPeakDays` controls in Core settings. `updateSettings` refreshes derived output and invokes reconciliation after mode, `postPeakDays`, or algorithm changes.

When the algorithm is disabled, no new inferred rows are created. Existing inferred rows are retained with provenance so logging-only mode does not destroy assumed data; re-enabling reconciliation evaluates them under the active mode. Changing `postPeakDays` moves the tail boundary and removes or regenerates only rows whose window basis is stale.

### 6. Surface provenance in the Calendar entry surface

The Calendar cell and day-entry dialog show an assumed/autogenerated marker for inferred rows while retaining the normal Low dot and derived status color. The marker is informational; the existing form remains the edit/delete path. Generated rows are not rendered as future data, and the existing no-future-write rule applies to reconciliation as well as manual entry.

## Risks / Trade-offs

- **Assumed rows look like real observations** -> Require an explicit marker in Calendar/dialog, keep origin in the stored row, and never relabel an edited row as an untouched generated assumption.
- **Generated rows influence cycle placement** -> Derive boundaries from authoritative user evidence first, then assign generated rows and verify the final placement; add store tests for stale-tail deletion and backfilled Menses.
- **Changing settings or adding a newer Peak invalidates rows** -> Store the inference basis and re-run reconciliation after every relevant write; only generated rows are removable.
- **A 30-row cap leaves later eligible-looking dates blank** -> Treat the cap as an intentional safety boundary; a cycle/window change is required before generation resumes.
- **Algorithm-off mode retains assumed data** -> Keep provenance and raw values visible where the existing logging-only contract requires readings to remain, but do not create new interpretation-dependent rows while off.

## Migration Plan

1. Add optional provenance fields with legacy rows defaulting to user-authored.
2. Add the persisted fill-mode and post-Peak suppression settings with safe defaults.
3. Add the pure planner and reconciliation tests before wiring the store transaction.
4. Enable reconciliation on hydration and after relevant user/settings writes; do not bulk-create rows until the planner and stale-row behavior pass.
5. Add Calendar/settings markers and controls, then run `pnpm test`, `pnpm lint`, and `pnpm build`.
6. Rollback is limited to disabling the algorithm or setting a non-generating mode; user-authored rows remain untouched. A future cleanup utility can remove inferred rows by origin and stale suppressions if needed.

## Scope Decision

- The MVP requires the provenance marker in the Calendar and daily-entry dialog. The cycle chart and history continue to treat the generated `monitor: low` as stored data; adding separate inferred-only visual treatments to those views is deferred so the fill/reconciliation contract is not coupled to optional presentation work.
