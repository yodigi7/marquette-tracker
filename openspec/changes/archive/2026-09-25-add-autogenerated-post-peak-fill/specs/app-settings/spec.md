# Spec Delta

## ADDED Requirements

### Requirement: Post-Peak fill mode is configurable and persisted

The Settings screen SHALL provide a persisted selector for the post-Peak fill mode with `auto-after-window` and `after-user-low` options. `auto-after-window` SHALL be the default. Changing the selector SHALL save immediately and SHALL cause the stored inferred tail to be reconciled without deleting user-authored records.

#### Scenario: Automatic mode is the default

- **WHEN** the user opens Settings without a previously saved fill mode
- **THEN** the selector shows `auto-after-window`
- **AND** the choice survives closing and reopening the app

#### Scenario: User-anchor mode is selected

- **WHEN** the user selects `after-user-low`
- **THEN** the setting is stored immediately
- **AND** future reconciliation waits for a qualifying user-entered post-Peak Low before generating records

#### Scenario: Changing mode reconciles generated data

- **WHEN** the user changes the fill mode
- **THEN** eligible autogenerated records are added or removed according to the new mode
- **AND** no user-authored record is deleted or overwritten

### Requirement: Fill behavior follows algorithm and post-Peak settings

When the fertile-window algorithm is disabled, the system SHALL pause creation of new autogenerated post-Peak records, preserve existing autogenerated records with their provenance, and resume reconciliation when interpretation is enabled again. Changing `postPeakDays` SHALL change the eligible tail boundary and SHALL reconcile previously generated records that no longer belong to that window.

#### Scenario: Algorithm off pauses new generation

- **GIVEN** a cycle has a known Peak and an eligible missing post-Peak date
- **WHEN** the user turns the algorithm off
- **THEN** no new autogenerated record is created
- **AND** existing generated records remain stored and marked as generated

#### Scenario: Re-enabling interpretation resumes reconciliation

- **WHEN** the user turns the algorithm back on
- **THEN** the system reconciles eligible post-Peak dates under the active fill mode
- **AND** no user-authored data is lost

#### Scenario: Post-Peak days change shifts the configured tail

- **WHEN** the user changes the post-Peak-day setting
- **THEN** the generated tail begins at the new configured boundary `peakDay + postPeakDays + 1`
- **AND** generated records outside the new eligible tail are removed or regenerated as appropriate
