# Spec Delta

## MODIFIED Requirements

### Requirement: Algorithm can be toggled off for logging-only

The Settings screen MUST provide an algorithm on/off switch, on by default. When off, no fertile-window interpretation SHALL be shown anywhere (no status on Status, no shading on the Calendar, no window band on the Cycle chart) while user-authored readings remain recorded and visible. Autogenerated post-Peak rows SHALL remain stored for later reconciliation but SHALL be hidden and ignored for interpretation and cycle placement while off. Switching it back on MUST restore interpretation from the same data.

#### Scenario: Default behaviour with the algorithm on
- **WHEN** the app is used with the algorithm switch on (the default)
- **THEN** Status shows a fertile-window status when a cycle result exists, and the Calendar and Cycle chart show window shading

#### Scenario: Logging-only mode
- **WHEN** the user switches the algorithm off and opens Status, the Calendar, or the Cycle chart, and logs a day's readings
- **THEN** no fertile-window status, shading, or window band is shown; user-authored readings are stored normally with no interpretation attached; all user-authored readings remain visible; and autogenerated rows are hidden

#### Scenario: Inferred data is retained but ignored
- **GIVEN** autogenerated post-Peak rows already exist
- **WHEN** the user turns the algorithm off
- **THEN** those rows remain stored with their provenance
- **AND** they do not affect cycle placement or appear in frontend interpretation

#### Scenario: Re-enabling interpretation
- **WHEN** the user switches the algorithm back on
- **THEN** interpretation resumes from the same records without any data loss
- **AND** eligible autogenerated rows are reconciled and shown again

### Requirement: Fill behavior follows algorithm and post-Peak settings

When the fertile-window algorithm is disabled, the system SHALL pause creation of new autogenerated post-Peak records, preserve existing autogenerated records with their provenance, exclude those records from cycle placement and derived output, hide them from the frontend, and resume reconciliation when interpretation is enabled again. Changing `postPeakDays` SHALL change the eligible tail boundary and SHALL reconcile previously generated records that no longer belong to that window.

#### Scenario: Algorithm off pauses new generation
- **GIVEN** a cycle has a known Peak and an eligible missing post-Peak date
- **WHEN** the user turns the algorithm off
- **THEN** no new autogenerated record is created
- **AND** existing generated records remain stored and marked as generated

#### Scenario: Algorithm off isolates existing generated rows
- **GIVEN** generated records already exist
- **WHEN** the user changes unrelated settings while the algorithm is off
- **THEN** existing generated records remain stored but are excluded from cycle placement, derived output, and frontend presentation

#### Scenario: Re-enabling interpretation resumes reconciliation
- **WHEN** the user turns the algorithm back on
- **THEN** the system reconciles eligible post-Peak dates under the active fill mode
- **AND** no user-authored data is lost

#### Scenario: Post-Peak days change shifts the configured tail
- **WHEN** the user changes the post-Peak-day setting
- **THEN** the generated tail begins at the new configured boundary `peakDay + postPeakDays + 1`
- **AND** generated records outside the new eligible tail are removed or regenerated as appropriate
