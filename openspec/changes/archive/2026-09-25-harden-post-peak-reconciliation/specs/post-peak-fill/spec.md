# Spec Delta

## ADDED Requirements

### Requirement: Algorithm-off mode isolates inferred data

When the fertile-window algorithm is disabled, the system SHALL retain autogenerated post-Peak Day Records in storage but SHALL exclude them from cycle placement, derived engine output, and frontend presentation. User-authored records SHALL remain visible and authoritative, and re-enabling the algorithm SHALL reconcile the retained inferred records under the active fill mode.

#### Scenario: Inferred rows do not affect cycle placement while off

- **GIVEN** autogenerated Low rows exist between user-authored records
- **WHEN** the fertile-window algorithm is disabled and cycle structure is re-derived
- **THEN** the inferred rows do not create, preserve, or move cycle boundaries
- **AND** only user-authored records and declared cycle starts determine placement

#### Scenario: Inferred rows are hidden while off

- **GIVEN** autogenerated Low rows exist in storage
- **WHEN** the algorithm is disabled
- **THEN** Calendar, Status, Cycle chart, and History do not show the inferred rows or their derived statuses
- **AND** user-authored records remain visible

#### Scenario: Re-enabling restores eligible inferred data

- **WHEN** the user re-enables the fertile-window algorithm
- **THEN** retained inferred rows are reconciled under the active fill mode
- **AND** eligible rows become visible with their inferred provenance

### Requirement: Hydration exposes only reconciled state

The app SHALL keep its loading state and SHALL NOT expose hydrated, renderable state until the initial post-Peak reconciliation has completed successfully. Persisted inferred rows and cycle assignments SHALL be refreshed before the app becomes renderable. If initial reconciliation fails, the app SHALL remain non-hydrated and SHALL NOT expose the unreconciled state as current.

#### Scenario: Stale persisted inference is reconciled before rendering

- **GIVEN** the database contains a stale inferred row or cycle assignment from a previous session
- **WHEN** the app starts and performs initial hydration
- **THEN** the app remains in its loading state while reconciliation runs
- **AND** the app becomes renderable only after the refreshed, reconciled state is available

#### Scenario: Failed initial reconciliation does not expose stale state

- **GIVEN** initial post-Peak reconciliation fails during hydration
- **WHEN** the hydration operation rejects
- **THEN** the store remains non-hydrated
- **AND** the app does not render the partially loaded or unreconciled state as current

### Requirement: Source mutations and reconciliation commit atomically

When a user day-record, deletion, settings, or cycle-start mutation can affect autogenerated post-Peak records, the system SHALL commit the source mutation and the resulting reconciliation outcome as one atomic unit. If reconciliation fails, the source mutation and any generated-row changes from that operation SHALL roll back together.

#### Scenario: Successful mutation commits a coherent tail

- **WHEN** a user mutation changes data that affects post-Peak inference and reconciliation succeeds
- **THEN** the user mutation and any required generated-row changes are committed together
- **AND** the store refreshes its derived output from that committed snapshot

#### Scenario: Failed reconciliation rolls back a day-record write

- **GIVEN** a day-record write would change the relevant post-Peak window
- **WHEN** reconciliation fails while processing the write
- **THEN** the day-record write is not left committed
- **AND** generated rows are not left partially reconciled

#### Scenario: Failed reconciliation rolls back settings and deletion changes

- **WHEN** a settings update or inferred-record deletion triggers reconciliation and reconciliation fails
- **THEN** the settings or deletion mutation is rolled back with its generated-row effects
- **AND** the prior persisted state remains coherent
