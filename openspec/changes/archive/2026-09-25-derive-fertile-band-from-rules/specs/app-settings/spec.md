# Spec Delta

## ADDED Requirements

### Requirement: Algorithm toggle controls interpretation only

The Settings screen MUST provide an algorithm on/off switch, on by default. When off, no fertile-window interpretation SHALL be shown anywhere (no status on Status, no shading on the Calendar, no window band on the Cycle chart) while user-entered readings remain recorded and visible. Turning it off SHALL NOT remove, hide, or otherwise set aside any stored reading, and cycle grouping SHALL continue to be derived from the same stored records. Switching it back on MUST restore interpretation from the same data.

#### Scenario: Default behaviour with the algorithm on

- **WHEN** the app is used with the algorithm switch on (the default)
- **THEN** Status shows a fertile-window status when a cycle result exists, and the Calendar and Cycle chart show window shading

#### Scenario: Logging-only mode

- **WHEN** the user switches the algorithm off and opens Status, the Calendar, or the Cycle chart, and logs a day's readings
- **THEN** no fertile-window status, shading, or window band is shown; user-entered readings are stored normally with no interpretation attached; and all stored readings remain visible

#### Scenario: Stored readings are untouched by the toggle

- **GIVEN** stored day records exist
- **WHEN** the user turns the algorithm off
- **THEN** every stored record remains present and visible
- **AND** cycle grouping continues to be derived from those records

#### Scenario: Re-enabling interpretation

- **WHEN** the user switches the algorithm back on
- **THEN** interpretation resumes from the same records without any data loss

## REMOVED Requirements

### Requirement: Algorithm can be toggled off for logging-only

**Reason**: The requirement is rewritten because its logging-only scenarios asserted behavior about autogenerated post-Peak rows — that they are hidden from the frontend, retained in storage, and excluded from cycle placement while the algorithm is off. The app no longer generates records, so those scenarios describe a condition that cannot occur and the requirement can no longer be modified in place without carrying them forward. The replacement requirement keeps the toggle's user-facing meaning, the default-on state, and the guarantee that stored readings are untouched.

**Migration**: Remove the inferred-row filtering branch from the algorithm-off path. Turning interpretation off now suppresses derived output only; stored records and cycle placement are unaffected either way.

### Requirement: Post-Peak fill mode is configurable and persisted

**Reason**: The fill mode decided when the app would generate stored Low records after the fertile window. The app no longer generates records, so the setting has no subject and no observable effect.

**Migration**: Remove the fill-mode selector from the Settings Core section, the `postPeakFillMode` field from settings and the backup document, and the post-Peak fill preferences from restored settings.

### Requirement: Fill behavior follows algorithm and post-Peak settings

**Reason**: This requirement described when generation paused while the algorithm was off, how existing generated rows were isolated from placement, and how changing `postPeakDays` shifted the generated tail. None of those behaviors remain once generation is removed. The `postPeakDays` setting itself is unaffected and continues to move the fertile-window end.

**Migration**: Remove the generated-row branches from the algorithm-off path. Changing `postPeakDays` continues to move the inclusive fertile-window end, and the derived band follows it on the next computation.
