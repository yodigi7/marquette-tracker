# Spec Delta

## ADDED Requirements

### Requirement: Calendar provides a phase-first cycle summary

The Calendar SHALL provide a compact summary above the day grid that identifies the current cycle number, cycle day, simplified fertility status, and current monitor reading when one is available. The summary SHALL remain readable at narrow mobile widths and SHALL NOT replace or prevent the day-entry interaction.

#### Scenario: Summary shows the current interpreted state
- **WHEN** the Calendar is displayed with interpretation enabled and a current cycle is available
- **THEN** the summary shows the cycle number, cycle day, `Before`, `Fertile`, or `After` status, and the current monitor reading when present

#### Scenario: Summary handles a missing monitor reading
- **WHEN** the current cycle or day has no monitor reading
- **THEN** the summary remains visible with a clear no-reading state rather than showing a misleading marker

#### Scenario: Summary remains useful while interpretation is disabled
- **WHEN** the algorithm is disabled
- **THEN** the summary remains visible with available cycle/day and raw information
- **AND** it clearly identifies the state as logging-only without showing a derived fertility status

#### Scenario: Summary handles no derived cycle
- **WHEN** no cycle has been derived for the current date
- **THEN** the summary shows a clear no-cycle state and does not invent a cycle number or status

### Requirement: Calendar supports simple and full-detail presentation

The Calendar SHALL use a simple phase-first presentation by default and SHALL provide an accessible way to reveal the richer existing indicators in a full-detail presentation. Changing presentation SHALL NOT change stored records, engine output, interpretation, or day-entry behavior.

#### Scenario: Simple presentation is the default
- **WHEN** the Calendar is opened without a previously selected full-detail preference
- **THEN** the grid emphasizes the simplified status, menses treatment, monitor reading, and assumed-data marker
- **AND** secondary indicators do not compete with those primary cues

#### Scenario: User reveals full detail
- **WHEN** the user enables the full-detail presentation
- **THEN** the richer existing indicators, including available intercourse, ovulation, source/forecast, and provenance cues, are available without changing any record

#### Scenario: Day details remain complete
- **WHEN** the user opens a day from either presentation
- **THEN** the existing full day-entry/detail surface remains available with all original fields and editing actions

### Requirement: Calendar uses a bottom menses stripe and one color-coded monitor marker

The Calendar SHALL represent recorded menses with a visible stripe along the bottom edge of the day cell. It SHALL use one common monitor marker shape and SHALL encode Low, High, and Peak by color, with the exact reading available through the summary, details, and accessible text.

#### Scenario: Menses is visible over a status background
- **WHEN** a Calendar day is a recorded menses day
- **THEN** the day cell shows the bottom menses stripe regardless of the cell's simplified status treatment

#### Scenario: Monitor reading is visible
- **WHEN** a Calendar day has a user or displayed monitor reading
- **THEN** the cell shows one monitor marker whose color identifies Low, High, or Peak
- **AND** Low, High, and Peak do not use different marker shapes

#### Scenario: Monitor value is available without decoding color
- **WHEN** a user inspects a day with a monitor marker
- **THEN** the exact Low, High, or Peak value is available in the summary, day details, or accessible label

## MODIFIED Requirements

### Requirement: Calendar identifies autogenerated records

The Calendar SHALL visually distinguish an autogenerated Day Record from a user-entered Day Record while continuing to show its stored monitor value. In the simple presentation, the Calendar SHALL mark an autogenerated record with an asterisk immediately beside the date number. The daily-entry dialog SHALL expose the same provenance and SHALL allow the user to edit or delete the record.

#### Scenario: Calendar cell marks an assumed Low

- **WHEN** a Calendar day contains an autogenerated Low record
- **THEN** the cell shows the stored Low reading and an asterisk beside the date number
- **AND** the asterisk does not identify the record as user-entered input

#### Scenario: User edits an assumed record

- **WHEN** the user opens an autogenerated record and saves a changed value
- **THEN** the changed record becomes user-authoritative
- **AND** the Calendar no longer presents it as an unchanged generated assumption

#### Scenario: User deletes an assumed record

- **WHEN** the user deletes an autogenerated record from the day-entry dialog
- **THEN** the Calendar removes the assumed-data asterisk
- **AND** a later reconciliation does not immediately recreate the deleted record

### Requirement: Calendar reflects reconciled post-Peak tails

The Calendar SHALL show only the generated records that are currently eligible under the active fill mode, post-Peak setting, cycle boundary, and reconciliation state when the fertile-window algorithm is enabled. Missing dates before an `after-user-low` anchor SHALL remain blank, while eligible generated records SHALL be shown with their stored Low marker, assumed-data asterisk, and simplified derived status. When the algorithm is disabled, the Calendar SHALL omit all autogenerated records from cells, dialogs, and derived presentation while continuing to show user-authored records.

#### Scenario: User-anchor mode leaves earlier gaps blank

- **GIVEN** the active mode is `after-user-low` and the first qualifying user Low occurs after gaps in the configured post-Peak tail
- **WHEN** the Calendar renders that cycle
- **THEN** dates before the user Low remain without generated records
- **AND** eligible generated dates after the user Low are shown

#### Scenario: New Menses closes the displayed tail

- **WHEN** the user backfills a Menses day that changes the cycle boundary
- **THEN** the Calendar re-renders the affected cycle without stale generated tail records
- **AND** the new Menses day begins the new cycle visually and structurally

#### Scenario: Future dates are not generated

- **WHEN** the Calendar reconciles an open cycle
- **THEN** no future cell receives an autogenerated record
- **AND** future cells remain subject to the existing future-date entry restriction

#### Scenario: Algorithm-off mode hides inferred rows

- **GIVEN** autogenerated post-Peak records exist in storage
- **WHEN** the fertile-window algorithm is disabled and the Calendar renders
- **THEN** no inferred Low marker, assumed asterisk, status, or inferred dialog content is shown
- **AND** user-authored records remain visible and editable

### Requirement: Intercourse heart marker

The Calendar SHALL preserve the small filled red heart treatment for recorded intercourse in the full-detail presentation and SHALL provide the same marker meaning there. The simple presentation MAY omit the heart from the day cell to reduce visual density, but the record SHALL remain available in the day-entry/detail surface.

#### Scenario: Intercourse recorded on a day
- **WHEN** a Calendar day has intercourse recorded and full detail is shown
- **THEN** the day cell displays a small filled red heart
- **AND** the former green dot is not used for intercourse

#### Scenario: Intercourse legend
- **WHEN** the full-detail Calendar legend is displayed
- **THEN** the Intercourse entry displays a small filled red heart
- **AND** the entry uses the same marker treatment as the full-detail day cell

#### Scenario: Intercourse is available in the simple presentation
- **WHEN** a Calendar day has intercourse recorded and the simple presentation is active
- **THEN** the day-entry/detail surface still exposes the intercourse value
- **AND** the simple grid is not required to show the heart

#### Scenario: No intercourse recorded
- **WHEN** a Calendar day has no intercourse record
- **THEN** the day cell does not display an intercourse heart

### Requirement: Calendar day cells use theme-aware derived-status treatments

The Calendar SHALL render recorded days in the default presentation using the three human-facing categories `Before` (`pre-fertile`), `Fertile` (`fertile`), and `After` (`post-peak` or `post-calendar`) with theme-appropriate treatments in both light and dark modes. The precise internal status SHALL remain available in the Status view, full-detail presentation, and accessible details. Unlogged days SHALL retain the existing blank/base treatment rather than receiving a new derived-status fill.

#### Scenario: Simplified statuses remain distinct
- **WHEN** the Calendar displays recorded days in the three simplified categories
- **THEN** each category has a readable and distinct treatment
- **AND** the day number remains readable

#### Scenario: Recorded statuses remain distinct in dark mode

- **WHEN** the Calendar displays recorded days in each of the three simplified categories in dark mode
- **THEN** each category has a readable, visually distinguishable treatment
- **AND** the day number remains readable against its treatment

#### Scenario: Unlogged days remain base cells

- **WHEN** a Calendar day has no Day Record
- **THEN** it does not receive a derived-status fill solely because the date falls inside a calculated window
- **AND** any existing forecast outline remains visibly predictive

#### Scenario: Algorithm-disabled mode hides interpretation styling

- **WHEN** the algorithm is disabled and the Calendar displays raw readings
- **THEN** simplified derived status fills and computed forecast styling are absent
- **AND** raw reading markers remain visible

### Requirement: Calendar distinguishes source, forecast, and provenance cues

The Calendar SHALL keep confirmed versus predicted status source, the future fertile-window forecast, predicted ovulation, raw-data markers, and inferred-data provenance distinct in the presentation where they are shown. The simple presentation MAY prioritize the phase, menses, monitor, and assumed cues and defer secondary cues to full detail or day details, but it SHALL NOT present a future forecast or inferred record as confirmed user data.

#### Scenario: Confirmed and predicted cells remain distinguishable
- **WHEN** recorded days share a simplified status but have different source values in the full-detail presentation
- **THEN** the user can distinguish their source cues in addition to the status treatment
- **AND** the status meaning remains unchanged

#### Scenario: Forecast cells remain visibly predictive
- **WHEN** a future date falls within the next fertile-window forecast
- **THEN** its treatment uses a predictive border, pattern, label, or equivalent cue
- **AND** it is not presented as a confirmed recorded status

#### Scenario: Assumed readings remain marked
- **WHEN** a Calendar day contains an inferred Day Record
- **THEN** the cell shows the stored reading and an assumed-data asterisk
- **AND** the marker is not presented as user-entered data

### Requirement: Calendar legend stays synchronized with day cells

The Calendar legend SHALL match the colors, borders, line styles, and marker shapes used in the active presentation. The default legend SHALL be grouped around the three simplified status categories, the menses stripe, the color-coded monitor readings, and the assumed-data asterisk. A full-detail legend SHALL additionally explain any secondary indicators that the full-detail presentation exposes.

#### Scenario: Simplified legend covers the default vocabulary
- **WHEN** the simple Calendar legend is displayed
- **THEN** it explains `Before`, `Fertile`, `After`, menses, monitor readings, and assumed data
- **AND** its samples match the corresponding day-cell treatments

#### Scenario: Post-calendar state is explained

- **WHEN** the Calendar legend is displayed
- **THEN** a legend entry describes the `After` treatment used for post-calendar cells
- **AND** the entry uses the same visual treatment as the corresponding day cell

#### Scenario: Full-detail legend covers extra indicators
- **WHEN** the full-detail presentation is displayed
- **THEN** the legend explains the additional visible source, forecast, ovulation, intercourse, or provenance indicators

#### Scenario: Theme-specific legend samples remain synchronized

- **WHEN** the user switches between light and dark themes
- **THEN** legend samples and day-cell treatments change together
- **AND** no legend sample refers to a stale light-only treatment

### Requirement: Calendar remains legible at narrow mobile widths

The Calendar SHALL keep the day number, simplified status, menses stripe, monitor marker, assumed-data asterisk, and future forecast cue distinguishable at narrow mobile viewport widths. The presentation SHALL use accessible text or equivalent non-color cues where color alone would not communicate a reading or provenance meaning.

#### Scenario: Narrow Calendar review

- **WHEN** the user views the Calendar at a narrow mobile width in either theme
- **THEN** the day number and important state cues remain visually separable
- **AND** the monitor reading and assumed provenance are available through accessible text or detail surfaces
- **AND** the most important status/forecast distinctions do not rely on color alone
